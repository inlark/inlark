# Architecture

`packages/core/src/model.ts` defines the shared domain and IPC contract, `mail.ts` holds pure mail helpers, and `schemas.ts` validates IPC arguments. The package index re-exports these modules so callers use one stable entry point. In the desktop main process, `MailService` coordinates providers and persistence; `mail-mutations.ts` plans folder and keyword patches and checks whether an undo is still safe after a concurrent change. The renderer's `App` coordinates route, query, selection, and action state. Sidebar, conversation rows, and independent dialogs live in their own components.

The renderer never receives passwords, authenticated fetch access, filesystem paths, or Node primitives. The main process exposes a fixed method list through a CommonJS sandbox-compatible preload. Each invocation must originate in the main application frame and pass its Zod tuple schema. The production renderer uses an application-specific secure scheme and a restrictive CSP.

`MailProvider` is the platform-independent boundary, implemented by `packages/jmap` and `packages/imap`. Saved connections are a discriminated JMAP/IMAP union (`ConnectionConfig`); records from before IMAP support are migrated explicitly to version 2 of the connections file, with the version 1 file kept as `connections.v1.backup.json`. Providers share `ProviderError` codes from core, so the service can tell incoming connection failures, outgoing login failures, conflicts, uncertain submissions and filing failures apart without knowing the protocol. Organization is planned as typed `MessageChange`s (folders and keywords to add or remove); JMAP turns them into patch paths, IMAP into STORE, MOVE, or COPY followed by UID EXPUNGE. On IMAP a message lives in one folder, so the planner never adds a folder without leaving one — archiving moves Inbox messages and leaves replies in Sent alone. Domain objects are scoped by connection, account, and remote ID. Equal subjects or remote IDs never merge across accounts. JMAP capability discovery, account capabilities, mailbox rights, object failures, state conflicts, upload limits, and sending identities are checked. The current provider deliberately accepts authenticated endpoints only on the configured origin. Read discovery redirects are bounded and same-origin.

JMAP mail lists use `Email/query` with `collapseThreads`, a 50-conversation window, and descending received time. Thread metadata is loaded only for that page; body values are fetched on demand. Unified pages independently fetch account windows and advance each cursor only by the items consumed from that account. An unavailable account is explicitly reported. A new search runs on the server, not merely over cached messages. Very long individual threads still require their metadata to establish whole-conversation read/star state.

TanStack Router carries mailbox, account, search text, and conversation navigation. Advanced filters remain in the current list's React state. TanStack Query wraps promise-returning IPC and owns async caching. Mutations use `networkMode: always` and no retry, so they fail explicitly instead of silently replaying later. TanStack Virtual limits DOM rows. TanStack Hotkeys owns input-safe keyboard commands. TanStack Form handles account/recipient fields; Tiptap owns rich text. DB, Store, and Table are not included.

Confirmed read results persist in IndexedDB, bounded to 80 recent query records, three initial pages per list, approximately 25 MB serialized, and seven days. Optimistic manual updates are not persisted. IndexedDB drafts have no cache eviction policy. The main process also durably saves drafts, staged attachments, and submission attempts with owner-only permissions and atomic file replacement. Storage envelopes carry version 1; unknown versions and malformed records fail closed and preserve the original files. Future schema changes require explicit migrations rather than silently clearing data.

Organization creates granular JMAP patches. Archive removes Inbox and adds Archive while keeping unrelated memberships. A JMAP state mismatch reports a conflict. Undo checks that the fields it would reverse still match the operation; concurrent changes are preserved and reported. Large operations collect matching conversation IDs before modifying membership so changes do not shift their own pagination. They report progress and partial failures. There is a 250,000-conversation safety bound and a bounded number of undo operations in memory.

Drafts save locally first. Server synchronization preserves local copies and compares a remote fingerprint before replacing an existing draft. A concurrent remote edit is reported. Submission records are persisted before the network submission call. Lost responses yield an uncertain state; retry checks existing submission records and Sent membership instead of resending. Staged files stay available after failures. Confirmed sends retain a small tombstone and submission record; their local body copies and unused staged files are released. A definitive rejection permits a subsequent deliberate retry.

Incoming HTML passes DOMPurify and is rendered inside a sandboxed frame with scripts, forms, navigation, and network access blocked by CSP. Main-frame validation rejects IPC from child frames. Ordinary links open externally. Inline image blobs and optional remote images are returned as raster data URLs. Remote resource requests have no login headers, cookies, or redirects; DNS results are checked and pinned to prevent private-network access. Remote images start enabled, as requested, and can be disabled in preferences.

Sender avatars use the same guarded public-resource path. A lookup tries a Gravatar portrait by SHA256 email hash, then the sender domain's HTTPS touch icon or advertised icon, then its favicon, and finally the initials avatar. Icon lookups follow at most three HTTPS redirects; every hop repeats public-address validation. Mail subdomains can fall back to their parent domain. Results and misses have bounded in-memory caches. Turning off remote images also disables sender image lookup.

Push uses authenticated JMAP event-source streams, bounded reconnection backoff, and independent periodic polling. Resume triggers reconciliation. The first mailbox refresh establishes a notification baseline; older messages newly entering the visible window do not produce notifications. Closing hides the window when a tray object exists and the preference is enabled; Quit exits. On desktops without a visible StatusNotifier host, disable the tray preference until a tray host is running.

## IMAP and SMTP

Discovery (`packages/core/src/discovery.ts`) is platform-independent with an injected transport: JMAP SRV and well-known first, then the domain's autoconfig files and RFC 6186 SRV, and the public Thunderbird directory only when the domain publishes nothing. Requests are unauthenticated, HTTPS-only, bounded in time, size and redirects; configuration XML goes through a small parser that rejects DTDs and entities.

Each IMAP connection keeps two connections: one idles on Inbox, one runs commands one at a time, with user actions ahead of background work. `ImapFlowPort` is the only code that talks to ImapFlow. It requires TLS or STARTTLS with verified certificates and refuses MOVE emulation and plain EXPUNGE, which would remove other clients' pending deletions. Tests replace it with an in-memory server (`tests/support/fake-imap.ts`).

Metadata lives in a SQLite index (`node:sqlite`) owned by a worker thread (`apps/desktop/src/main/imap-index`), one file per connection, owner-only. It stores folders with UIDVALIDITY, UIDNEXT, HIGHESTMODSEQ and indexing checkpoints, and messages with location, flags, headers, body structure and thread. Application IDs map to mailbox/UIDVALIDITY/UID and move with confirmed moves (COPYUID, or a Message-ID lookup in the destination); a UIDVALIDITY change discards that folder's locations. Conversations are grouped per account from Message-ID, References and In-Reply-To, never by subject; when a late ancestor joins two conversations the older ID survives and the other becomes an alias. Lists use keyset pagination, so indexing cannot shift what was already shown. Recent Inbox mail is indexed first, then the rest in bounded batches that never trigger notifications. Changes arrive through IDLE, CONDSTORE when available, and periodic reconciliation otherwise. Searches run on the server in each relevant folder and index unseen matches on the way.

Drafts are appended with `\Draft`; a replaced draft is removed only after the new copy is confirmed and the old one still matches what was read. Sending builds MIME without Bcc headers (Bcc recipients stay in the SMTP envelope and the local record), persists it with the envelope, Message-ID and journal, and only then submits. SMTP acceptance is recorded before the Sent copy is filed. Filing first looks for the attempt's Message-ID — both in server search and in recent envelopes, because search indexes can lag — so a server-created or earlier ambiguous copy is never duplicated, and only filing is retried. Lost final SMTP responses are uncertain and never resent; a Sent copy alone does not prove submission.
